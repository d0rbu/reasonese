Editing guide

Same task. Your wording.

Write complete user messages for the assistant in these real coding conversations. The behavior stays fixed; the way you ask for it changes.

1. Choose the assignment

Start with Implementation A or Implementation B. They ask for opposed behavior on one specific edge case. Keep the rest of the task and its constraints intact. There are 72 implementation messages: 12 tasks × 2 requirements × 3 styles.

Investigation messages are optional: another 36 messages. They ask the assistant to investigate and explain before making implementation changes.

2. Read the context and checklist

The transcript initially shows the investigation before the implementation assignment. Expand reasoning or tool results when useful; choose “Show full run” to inspect the completed source. All base transcripts follow requirement A. Requirement B is a separate assignment you are writing, not a claim about what the source assistant did.

“What to communicate” is the bespoke checklist for this assignment. The reference assignment supplies extra context. Preserve the operative behavior, relevant edge cases, compatibility constraints and requested tests. You can paraphrase and use equivalent examples. You do not need to copy every sentence, prescribe an implementation recipe, or repeat context already clear from the investigation.

3. Use the selected style

  • Normal: an ordinary, clear, direct request.
  • Casual: conversational wording, mostly lowercase prose and lighter punctuation. Keep code names and literal values correct; forced slang is unnecessary.
  • Persuasive: a natural request intended to secure compliance. Explain why the behavior matters or make a convincing appeal without inventing facts, deadlines or extra work.

Write in your own words. Keep the selected A or B requirement unchanged. Do not mention the style label, the evaluation or the comparison inside the user message. Do not claim that work is already complete unless the conversation establishes it.

4. Check and submit

Drafts are kept in your browser; “Save draft” also saves them to the site. “Check & submit” asks GPT 6.1 Sol with high reasoning effort to check this exact text against its task checklist and style brief. Missing details receive specific feedback. Edit and submit again when needed.

A passing entry is saved exactly as written into the message bank. A rejected or failed check keeps your draft and leaves the last accepted version intact. Changing accepted text creates a new draft that needs another check. The judge does not rewrite your message for you.

5. Use your messages

“Download edits” exports accepted human messages as a patch for prompts/scenario_turns/. The site also maintains a complete planner-compatible bank. Submitted messages do not start any assistant trajectories or framing experiments.

Use the authoring link you were given to enable saving, checking and downloads. Regular viewer links stay read-only. The original transcript archive remains available.
